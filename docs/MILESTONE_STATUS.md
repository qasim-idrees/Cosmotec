## Round 3 addendum

Model List, Basic Information, and category filters confirmed to share
one underlying specification data source — no separate "columns table"
or "basic info table" exists. Multi-value specification handling
(Milestone 8) is now a closed decision, not an open question: EC-CUBE's
own code takes the first value and discards the rest, so Magento will
do the same. Product detail page tabs beyond Model List (Catalog,
Assembly method, FAQ, etc.) are confirmed to be static Twig HTML, not
database-driven — explicitly out of scope for data migration, a
presentation-layer task if ever needed. See
`ECCUBE_FORENSIC_DATA_FLOW_ANALYSIS.md` Round 3 section for full detail
and confidence classification per finding.

## Round 4 addendum

Attribute Set strategy resolved empirically (one set per top-level
category, evidenced across all 1,073 items with specification data —
not just inferred from a handful of examples). Related Products fully
traced and confirmed structurally distinct from Connection Parts
(child-level vs. parent-level). Representative-image-selection for
category/Item listings remains genuinely untraced (would require
searching EC-CUBE core, not just app/Customize/). See
`ECCUBE_FORENSIC_DATA_FLOW_ANALYSIS.md` Round 4 for full detail and
the honest list of what's still open — none of it blocks starting
implementation.

## Bottom line

Nothing needs to be rebuilt. The gap is entirely **new** entity types
(Attributes, Attribute Sets, Product Attribute Values, Related Products,
Coupling Products) layered onto an architecture that already knows how to
support them — plus batching the write path once volume is confirmed.
